# Contributing to Kabul

Layout, local commands and general rules are in the [contributing guide](docs/guide/contributing.md).
This file covers commits, versions, the changelog, CI and releases.

## Commits: Conventional Commits

Every commit subject follows [Conventional Commits](https://www.conventionalcommits.org):

```
<type>(<optional scope>): <description>

<optional body>

<optional footers>
```

| Type | When | Version bump |
|---|---|---|
| `feat` | a new feature for users | minor |
| `fix` | a bug fix | patch |
| `perf` | faster or lighter, same behaviour | patch |
| `refactor` | code change without behaviour change | none |
| `docs` | documentation only | none |
| `test` | tests only | none |
| `build`, `ci` | build system, dependencies, workflows | none |
| `chore`, `style` | maintenance, formatting | none |
| `revert` | reverts a previous commit | depends |

- Scopes are the area touched: `core`, `cli`, `kabuld`, `desktop`, `web`, `mobile`, `docs`, `ci`.
- Breaking changes: `feat(core)!: ...` or a `BREAKING CHANGE: ...` footer. Before 1.0 a breaking change bumps the minor version.
- Type and scope are always in English; the description may be in English or Portuguese (the changelog keeps the commit's language).
- Examples: `feat(desktop): automatic updates with stable and beta channels`, `fix(web): composer keeps the draft after switching tabs`.

## Versions

Kabul uses [SemVer](https://semver.org) with **one version for the whole repo**. The source of truth is
`[workspace.package] version` in the root `Cargo.toml` (every crate inherits it with
`version.workspace = true`). `scripts/version.mjs` keeps `apps/web/package.json`,
`apps/desktop/package.json`, their lockfiles, `apps/desktop/src-tauri/tauri.conf.json` and `Cargo.lock` in sync:

```sh
node scripts/version.mjs get           # current version
node scripts/version.mjs set 0.10.0    # write it everywhere
node scripts/version.mjs check         # fails if anything diverges (runs in CI)
```

0.x until Kabul covers its daily use end to end; 1.0 when feature parity, Windows and the phone are stable.

### Formats on disk and the kabuld protocol

Files written by Kabul carry `schema_version` (`state.json`, `app-settings.json`, `settings.toml`,
`accounts.json` and the canonical transcript). To change a format, bump its constant in
`crates/kabul-core/src/schema.rs`, append the migration `vN -> vN+1` to that file's list and add a test
with a sample of the previous version. The original file is kept as `<file>.v<N>.bak` before migrating.

The WebSocket between kabuld and its clients has a protocol version (`schema::PROTOCOL`, mirrored in
`apps/web/src/version.ts`). Bump it only when one side stops understanding the other; new optional fields
or commands do not need a bump. A client that is too old gets a friendly "update Kabul" message instead of
errors.

## Changelog

`CHANGELOG.md` is generated by [git-cliff](https://git-cliff.org) from the commits (`cliff.toml`).
Commits that are not conventional do not appear. Preview the next release with:

```sh
npx git-cliff --unreleased
```

## CI

`.github/workflows/ci.yml` runs on every push to `main` and every pull request:

- the versions are in sync (`scripts/version.mjs check`);
- `cargo fmt --check` (style in `rustfmt.toml`), `cargo clippy -D warnings` and `cargo test` on macOS and Windows (Windows reports but does not block until the port lands, see `docs/windows.md`);
- `npm ci`, `npm run build` and the Playwright E2E suite against the mock backend on Linux and macOS (`KABUL_E2E_MOCK_ONLY=1` skips the `*-real` specs, which need the real core, `gh` and agents).

`main` is protected: changes go through pull requests with CI green.

## Releases

1. Bump: `node scripts/version.mjs set 0.10.0` (pre-releases: `0.10.0-beta.1`).
2. Changelog: `npx git-cliff --unreleased --tag v0.10.0 --prepend CHANGELOG.md`, then review the text.
3. Commit `chore(release): 0.10.0`, open the PR and merge it.
4. Tag the merge commit and push the tag: `git tag v0.10.0 && git push origin v0.10.0`.

`.github/workflows/release.yml` then checks the tag against the manifests, drafts a GitHub Release with
that version's changelog section, and builds the desktop app with
[tauri-action](https://github.com/tauri-apps/tauri-action): macOS Apple Silicon and Intel (`.app`, `.dmg`)
and Windows (`.msi`, NSIS `.exe`). Review the draft and publish it. Tags with a `-` (for example
`-beta.1`) become pre-releases.

### Signing (optional secrets)

Each kind of signing runs only when its secrets exist; without them the build still succeeds.

| Secret | Purpose |
|---|---|
| `TAURI_SIGNING_PRIVATE_KEY`, `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` | signs the update bundles and publishes `latest.json` (auto-update) |
| `APPLE_CERTIFICATE` (base64 `.p12`), `APPLE_CERTIFICATE_PASSWORD`, `APPLE_SIGNING_IDENTITY` | macOS code signing (without it: ad-hoc signature, Gatekeeper warns) |
| `APPLE_ID`, `APPLE_PASSWORD` (app-specific), `APPLE_TEAM_ID` | notarization |
| `WINDOWS_CERTIFICATE` (base64 `.pfx`), `WINDOWS_CERTIFICATE_PASSWORD` | Authenticode signing of the installers |

### Automatic updates

The app uses `tauri-plugin-updater`. Each update is verified against the public key in
`apps/desktop/src-tauri/tauri.conf.json` (`plugins.updater.pubkey`). The private key **never** goes in
the repository: the maintainer keeps it at `~/.config/kabul/updater.key` (mode 600, created with
`npx tauri signer generate -w ~/.config/kabul/updater.key`) and stores its contents as the
`TAURI_SIGNING_PRIVATE_KEY` secret of the repository (`gh secret set TAURI_SIGNING_PRIVATE_KEY < ~/.config/kabul/updater.key`).
If the key is lost, generate a new pair, replace `pubkey` and ship a release by hand: installed apps only
accept updates signed with the key they know.

Channels (Settings › Advanced › "Automatic updates" and "Update channel"):

- **stable** reads `releases/latest/download/latest.json` (the latest published release; pre-releases are skipped);
- **beta** reads `releases/download/beta/latest.json`: when any release is published, the workflow copies its `latest.json` to the rolling `beta` pre-release, so beta users get betas and stable versions alike.

The repository of those URLs is compiled into the app from `KABUL_UPDATE_REPO` (the CI passes
`github.repository`). The check runs a few seconds after launch, only in packaged builds; offline it just
reports "no connection" and tries again on the next launch. Installing always waits for the user's click.
